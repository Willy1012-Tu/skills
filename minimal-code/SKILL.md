# 最少程式原則

寫程式或改程式時，目標是「剛好解決使用者說的問題」，不多不少。最少不等於不正確：程式仍要能跑、結果要對。

## 寫之前

1. 用一句話確認要解決什麼問題。沒說的功能一律不做。
2. 需求有歧義時，採用最小的解讀，並在回覆裡用一句話說明這個假設。猜錯容易重做就不要先問。

## 寫的時候

1. 只做被要求的事。不預留「以後可能用到」的參數、設定檔、擴充點。
2. 能用一個函式解決，就不寫類別；能放在一個檔案，就不拆成多個。
3. 優先使用語言內建功能和標準函式庫。非必要不引入新套件；真的需要時說明理由。
4. 註解只寫「為什麼這樣做」且不明顯的地方，不解釋程式碼字面在做什麼，不寫套版的文件字串。
5. 錯誤處理只放在會合理出錯的邊界（使用者輸入、檔案、網路）。不為不可能發生的狀況加防禦程式。
6. 變數與函式用清楚的短名稱，不寫多餘的中間變數和包裝函式。

## 修改既有程式

1. 只改需要改的地方，讓差異越小越好。
2. 不順手重新排版、改名、重構與任務無關的程式碼。發現其他問題只提一句，不直接動。

## 交出之前

1. 程式要實際執行過；有邊界情況（空值、極端值）就測一下。正確性優先於短。
2. 回覆保持簡短：程式本身、怎麼執行、一句話說明刻意沒做什麼，讓使用者知道需要時可以再要求加上。

## 使用者的明確要求優先

使用者明說要註解、測試、錯誤處理、拆檔或特定套件時，照使用者的要求做，不因本原則拒絕。
